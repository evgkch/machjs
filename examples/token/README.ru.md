# Обновление токена

Полный разбор от постановки задачи до работающего автомата: HTTP-клиент, у которого истекает токен доступа, пять запросов, отказанных разом, и ровно одно обновление. Разделы идут в порядке работы — сначала граф переходов, затем контекст, операции, подключение к странице и анализ. В коде определения типов обычно стоят перед схемой; здесь они появляются по мере необходимости.

Обозначения и определения даны в [руководстве](https://github.com/evgkch/machjs/blob/master/README.ru.md). Ссылки вида «п. 4.2» указывают на разделы этого документа; на руководство ссылаемся по названию раздела — «README, „Схема переходов“».

**Рабочий проект.** Пример открывается как страница — [живая версия](https://evgkch.github.io/machjs/token/). Vite, обычный HTML и TypeScript, без фреймворков; команды выполняются из корня этого репозитория:

```sh
npm install
npm run dev       # http://localhost:5173/token/
npm run build     # tsc --noEmit + сборка в dist/
npm test          # каждая страница прогоняется в DOM
```

## 1. Постановка задачи

HTTP-клиент держит токен доступа. Просроченный токен сервер отклоняет ответом 401, и есть отдельная ручка, которая выдаёт новый. Шесть требований:

1. Запрос уходит с тем токеном, который держит клиент.
2. Ответ 401 означает: получить новый токен и повторить запрос.
3. Обновление запускается **один раз**, сколько бы запросов ни отказали в один момент. Остальные ждут.
4. Обновление удалось — каждый ждущий повторяется с новым токеном.
5. Обновление упало — каждый ждущий получает отказ. Никто не висит.
6. Второй 401, уже со свежим токеном, — это ответ, а не следующий круг.

На требовании 3 обычный код и ломается. Флаг `let refreshing = false` — очевидный способ его записать, и он же — способ подвесить все запросы процесса при первом же исключении в обновлении: флаг остаётся поднятым, очередь не разбужена, и каждый следующий запрос встаёт в неё же.

## 2. Что внутри автомата, а что снаружи

Запросов в автомате нет.

Запрос — это то, что держит страница: у него есть номер, строка на экране и обещание, которого кто-то ждёт. Автомат держит одно — состояние токена, и это разделение и есть замысел:

| В автомате                        | На странице                     |
| --------------------------------- | ------------------------------- |
| Есть ли годный токен              | Список запросов                 |
| Идёт ли обновление                | Что показывает каждая строка    |
| Сколько запросов ждёт             | Обещание, которого ждёт вызов   |
| Известно ли, что токена не будет  | Подставной сервер               |

Пять запросов, отказанных разом, — это пять строк на странице и **пять событий** автомату, из которых первое порождает `refresh`, а остальные четыре — нет. В этой разнице всё требование 3, и п. 5 показывает, что она умещается в одну ячейку.

## 3. Контекст

`Q` — носитель: состояние ↦ то, что несёт состояние (README, «Носители»):

```ts
export type Q = Merge<
  | IState<"ok", { token: Token }>
  | IState<"refreshing", { waiting: number }>
  | IState<"dead", { why: string }>
>;
```

Три фазы, три разных набора полей, и два отсутствия значат столько же, сколько три поля.

**У `refreshing` нет токена.** Пока новый добывается, старый заведомо отклонён, отправлять нечего — и дотянуться до него нельзя, потому что в `Q["refreshing"]` такого поля нет. Ошибка «отправили просроченный токен» здесь не предотвращается проверкой: её нельзя написать.

**У `dead` токена тоже нет.** Вместо него причина, и причина — это то, что уходит всем ждущим.

Алфавиты:

```ts
export type Σ = Merge<
  | IEvent<"denied">
  | IEvent<"renewed", { token: Token }>
  | IEvent<"failed", { why: string }>
  | IEvent<"retry">
>;

export type Λ = Merge<
  | IEvent<"refresh">
  | IEvent<"wake", { token: Token }>
  | IEvent<"giveUp", { why: string }>
>;
```

`denied` — одна буква на две ситуации: запрос отклонён с 401 и запрос пришёл, когда отправлять было нечем. Со стороны токена это одно и то же событие — ещё одному вызову нечего отправить, — поэтому буква одна, и страница их тоже не различает.

## 4. Операции

Каждая возвращает контекст той фазы, в которую автомат входит.

```ts
const first = (): { waiting: number } => ({ waiting: 1 });

const queue = (c: { waiting: number }): { waiting: number } => ({
  waiting: c.waiting + 1,
});

const accept = (_c: unknown, p: { token: Token }): { token: Token } => ({
  token: p.token,
});

const sorry = (c: { why: string }): { why: string } => ({ why: c.why });
```

`first` не переносит старый токен: его только что отклонили. `accept` читает новый из нагрузки, а не из контекста — в `refreshing` его нет, — и та же функция служит для `BY` события `wake`, потому что `by` выполняется на достигнутом контексте (README, «Выходные события»). Наружу уходит то, что только что записано, а не вторая копия, которая может с ним разойтись.

## 5. Схема

```ts
export const auth = new StateMachine<Q, Σ, Λ>(
  {
    ok: {
      denied: [{ to: ["refreshing", first], emit: "refresh" }],
    },
    refreshing: {
      denied: [{ to: ["refreshing", queue] }],
      renewed: [{ to: ["ok", accept], emit: ["wake", accept] }],
      failed: [{ to: ["dead", note], emit: ["giveUp", sorry] }],
    },
    dead: {
      denied: [{ to: "dead", emit: ["giveUp", sorry] }],
      retry: [{ to: ["refreshing", again], emit: "refresh" }],
    },
  },
  { type: "ok", context: { token: FIRST } },
);
```

Три места стоит прочесть дважды.

**Требование 3 — это ячейка, а не флаг.** `emit: "refresh"` стоит в `ok · denied` и больше нигде в этом столбце. `denied` второго вызова приходит в `refreshing`, где правило другое: оно считает ждущего и ничего не порождает. Проверки `if (refreshing)` нет, потому что ломаться нечему — в схеме нет способа запустить второе обновление.

**Требование 5 — это фаза с правилами.** `failed` ведёт в `dead`, и в `dead` для `denied` есть правило: каждый следующий вызов получает отказ сразу, с причиной. У несброшенного флага правил нет.

**`dead` — не тупик.** Уберите два его правила, и `validate` найдёт это (п. 8). Клиент, который после одного упавшего обновления отказывает всем до конца сессии, — ошибка, а не замысел, и различает их анализ.

## 6. Работа из браузера

Один запрос, от первой отправки до окончательного ответа. Фазу автомата здесь не спрашивают, чтобы решить, добывать ли токен:

```ts
async function ask(): Promise<void> {
  const row = line(++asked);
  const at = auth.state;
  let token = at.type === "ok" ? at.context.token : null;

  if (token === null) {
    say(row, "waiting", "no token — waiting");
    const got = await refused();
    if ("why" in got) return say(row, "refused", got.why);
    token = got.token;
  }

  say(row, "sent", `sent with ${token}`);
  if ((await send(token)) === 401) {
    say(row, "waiting", "401 — waiting for a token");
    const got = await refused();
    if ("why" in got) return say(row, "refused", got.why);
    token = got.token;
    say(row, "sent", `sent again with ${token}`);
    if ((await send(token)) === 401)
      return say(row, "refused", "401 with a fresh token");
  }
  say(row, "done", `200 with ${token}`);
}
```

`at.type === "ok"` — не проверка фазы вместо решения, а единственный способ прочитать токен: вне `ok` этого поля не существует, и компилятор требует сужения. А что делать, если токена нет, решается не здесь:

```ts
function refused(): Promise<{ token: Token } | { why: string }> {
  return new Promise((settle) => {
    queue.push(settle);
    auth.dispatch("denied");
  });
}
```

Запустило ли это обновление, встало ли в очередь или получило отказ сразу — определяет схема. Требования 3 в этом файле нет вовсе.

И никто не зависает — причём проверяется это чтением схемы, а не страницы: вызов ждёт обещания, которое разрешают только `wake` и `giveUp`, а **каждый путь из `refreshing` порождает одно из двух**.

## 7. Прогон автомата

Пять запросов, отказанных разом, и удачное обновление. Настоящий вывод теста этой страницы:

```text
PASS  refreshing — the legend follows: refreshing
PASS  five waiting: 5
PASS  and one fetch, not five: 1
PASS  no token in refreshing: false
PASS  back to ok: ok
PASS  the waiting were woken once: 1
PASS  with the new token: tok-1
```

Те же пятеро, но обновление сломано:

```text
PASS  dead — the legend follows: dead
PASS  the waiting were refused: 1
PASS  and a later caller is refused at once: true
PASS  refused, not queued: 2
PASS  the way back is offered: true
```

Строка `and one fetch, not five` — это требование 3, посчитанное, а не доказанное рассуждением. `refused, not queued` — требование 5: вызов, пришедший уже после падения обновления, получает отказ во время собственного `dispatch`, ни в какую очередь не вставая.

## 8. Анализ схемы

`validate` по схеме в текущем виде, вывод реального прогона:

```text
(находок нет)
```

`analyze`:

```text
{"nodes":["ok","refreshing","dead"],"reachable":["ok","refreshing","dead"],
 "unreachable":[],"terminal":[]}
```

Поле `terminal` пусто, и это утверждение о клиенте, а не о коде: фазы, из которой нет выхода, у него нет. Уберите два правила `dead` — а именно так обычно и выглядит та же программа, написанная на `switch`, — и тот же вызов выдаёт:

```text
⚠ warning node "dead" has no outgoing transitions
```

Одно упавшее обновление — и клиент отказывает всем до перезагрузки страницы. Чтобы это найти, ничего не выполнялось: автомат не запускался, ни одна операция не вызывалась.

Схема, распечатанная библиотекой:

```text
FROM ok         ON denied  TO refreshing WITH first  EMIT refresh
FROM refreshing ON denied  TO refreshing WITH queue
FROM refreshing ON renewed TO ok         WITH accept EMIT wake    BY accept
FROM refreshing ON failed  TO dead       WITH note   EMIT giveUp  BY sorry
FROM dead       ON denied  TO dead                   EMIT giveUp  BY sorry
FROM dead       ON retry   TO refreshing WITH again  EMIT refresh
```

Шесть предложений. Требование 3 — это отсутствие `EMIT refresh` во втором из них.
