# Две машины через канал

Полный разбор от постановки задачи до двух работающих автоматов: платёжный терминал и хост авторизации, соединённые каналом, который можно разорвать, замедлить и заставить доставить сообщение дважды. Разделы идут в порядке работы: сначала два графа переходов, затем контексты, условия и операции, затем стык между машинами, канал, подключение к странице и анализ. В коде определения типов обычно стоят перед схемой; здесь они появляются по мере необходимости.

Обозначения и определения даны в [руководстве](https://github.com/evgkch/machjs/blob/master/packages/core/README.ru.md). Ссылки вида «п. 4.2» указывают на разделы этого документа; на руководство ссылаемся по названию раздела, например «README, „Схема переходов“».

**Рабочий проект.** Пример открывается как страница: [живая версия](https://evgkch.github.io/machjs/wire/). Vite, обычный HTML и TypeScript, без фреймворков; команды выполняются из корня этого репозитория:

```sh
npm install
npm run dev       # http://localhost:5173/wire/
npm run build     # tsc --noEmit + сборка в dist/
npm test          # каждая страница прогоняется в DOM
```

## 1. Постановка задачи

Задача: платёжный терминал принимает сумму и отправляет хосту авторизации запрос на списание. У хоста есть остаток, и в ответ приходит согласие или отказ. Между ними сеть, и сеть ненадёжна: сообщение идёт произвольное время, доставляется дважды или не доходит вовсе.

Три свойства должны выполняться при любом поведении сети.

Ответ относится к одному запросу. Ни ответ на прошлую попытку, ни повторная доставка того же ответа не меняют состояние терминала.

Запрос списывает один раз. Если сеть доставила один и тот же запрос дважды, остаток меняется однократно. На вторую доставку приходит ответ, потому что отправитель не отличает её от первой, но больше ничего не происходит.

Ни одна машина не зависает из-за другой. Терминал, чей запрос потерян, остаётся там, где стоит, и показывает это; он не подставляет ответ и не переходит в состояние, для которого нет основания.

## 2. Две машины, а не одна

Пару можно было бы записать одной машиной над объединением обоих множеств состояний. Здесь она записана двумя, и причины стоит назвать до кода.

Первая причина: общего контекста нет. Терминал держит номер карты и сумму, а хост держит остаток и список выданных ответов. Ни одному из них не нужны поля другого, а единый `Q` внёс бы оба набора в каждое состояние.

Вторая причина: канал. Переход одной машины атомарен, и `dispatch` возвращает управление после того, как весь шаг выполнен (README, «Выполнение перехода: `dispatch` и `can`»). У двух машин, разделённых сетью, такого шага нет: запрос уходит из одной и приходит в другую позже или не приходит вовсе. Ни одна из машин не стоит в этом промежутке.

Поэтому стык состоит ровно из одного: выходной алфавит Λ терминала переносится во входной алфавит Σ хоста и обратно.

Таблица 1 — Что пересекает канал

| Сообщение | Откуда   | Что несёт                 | Чем становится      |
| --------- | -------- | ------------------------- | ------------------- |
| `auth`    | терминал | `{ ticket, pan, amount }` | событие `auth` хоста |
| `said`    | хост     | `{ ticket, ok, why }`     | событие `said` терминала |

`ticket` есть в обоих. Это единственный способ сопоставить ответ с запросом; порядок прихода сообщений не используется ни одной из машин.

## 3. Графы переходов

### 3.1 Терминал

Таблица 2 — Состояния терминала

| Состояние  | Значение                                                    |
| ---------- | ----------------------------------------------------------- |
| `idle`     | Ничего не введено                                           |
| `entering` | В поле есть цифры                                           |
| `waiting`  | Запрос отправлен, его номер лежит в контексте               |
| `approved` | Хост списал сумму                                           |
| `declined` | Хост отказал, либо читатель прекратил ожидание              |

Таблица 3 — События терминала

| Событие  | Нагрузка    | Источник                     |
| -------- | ----------- | ---------------------------- |
| `key`    | `{ digit }` | Клавиатура                   |
| `rub`    | —           | Backspace                    |
| `send`   | —           | Клавиша отправки             |
| `said`   | `Say`       | Хост, через канал            |
| `giveUp` | —           | Читатель прекращает ожидание |
| `again`  | —           | Начать заново                |

Таблица 4 — Правила терминала

| Откуда     | Событие  | Условие    | Куда       | Выход  |
| ---------- | -------- | ---------- | ---------- | ------ |
| `idle`     | `key`    | —          | `entering` | —      |
| `entering` | `key`    | —          | `entering` | —      |
| `entering` | `rub`    | `lastOne`  | `idle`     | —      |
| `entering` | `rub`    | —          | `entering` | —      |
| `entering` | `send`   | `payable`  | `waiting`  | `auth` |
| `waiting`  | `said`   | `yes`      | `approved` | —      |
| `waiting`  | `said`   | `no`       | `declined` | —      |
| `waiting`  | `giveUp` | —          | `declined` | —      |
| `approved` | `again`  | —          | `idle`     | —      |
| `declined` | `again`  | —          | `entering` | —      |

В `waiting` нет правила на `key` и нет правила на `rub`. Этим и исчерпывается блокировка клавиатуры на время ожидания: `dispatch("key", …)` из `waiting` не находит ячейки, возвращает `UNHANDLED` и ничего не меняет (README, «Частичность»). Ни один флаг для этого не заводится и ни один обработчик не отключается; в п. 9 страница читает тот же факт из машины обратно.

В `waiting` два правила на `said`, и оба с условиями. Ответ о другом номере не проходит ни одно из них, и `dispatch` возвращает `REJECTED`. Дубликат и опоздавший ответ попадают в один и тот же случай, и отдельного кода для него нет.

### 3.2 Хост

Таблица 5 — Состояния хоста

| Состояние   | Значение                        |
| ----------- | ------------------------------- |
| `listening` | Простой: есть остаток и список  |
| `working`   | Идёт проверка одного запроса    |

Таблица 6 — События хоста

| Событие | Нагрузка     | Источник                   |
| ------- | ------------ | -------------------------- |
| `auth`  | `Ask`        | Терминал, через канал      |
| `ready` | `{ ticket }` | Завершение проверки        |

Таблица 7 — Правила хоста

| Откуда      | Событие | Условие  | Куда        | Выход  |
| ----------- | ------- | -------- | ----------- | ------ |
| `listening` | `auth`  | `known`  | `listening` | `said` |
| `listening` | `auth`  | —        | `working`   | —      |
| `working`   | `ready` | `afford` | `listening` | `said` |
| `working`   | `ready` | `mine`   | `listening` | `said` |

В первой ячейке стоит каскад условий, и порядок в нём составляет всю идемпотентность. Узкий случай `known` стоит первым: на номер, ответ по которому уже выдан, ответ берётся из списка, без входа в `working` и без изменения остатка. Правило без условия под ним принимает остальное. В обратном порядке второе правило не сработало бы никогда, и в выводе `validate` появилась бы находка `dead-rule` (README, «`validate`»).

В `working` нет правила на `auth`. Запрос, пришедший во время проверки, отклоняется, и в п. 9 страница записывает этот отказ в журнал.

## 4. Контексты

В `Q` записан носитель: состояние ↦ то, что несёт состояние (README, «Носители»). Явная запись делает поле недоступным там, где оно не имеет смысла.

```ts
export type Card = { readonly pan: string; readonly ticket: number };
export type Typed = Card & { readonly typed: string };
export type Flight = Card & { readonly amount: Cents };
export type Done = Flight & { readonly why: string };

export type TQ = Merge<
  | IState<"idle", Card>
  | IState<"entering", Typed>
  | IState<"waiting", Flight>
  | IState<"approved", Done>
  | IState<"declined", Done>
>;
```

Счётчик номеров лежит в контексте, и это не деталь оформления. Операция остаётся чистой функцией от `(context, payload)` (README, «Операции»). Функция `next()`, увеличивающая переменную вне машины, дала бы для одной схемы два разных прогона, и повтор записанного прогона разошёлся бы с самим прогоном. `booked` читает `ticket + 1` (п. 6), а ожидаемый номер записан в контексте того состояния, где терминал ждёт.

Поле `typed` есть в `entering` и больше нигде, поэтому нет состояния, в котором терминал держит недовведённые цифры и при этом не находится в режиме ввода. Поле `why` есть только там, где есть что показать.

Контекст хоста состоит из двух полей:

```ts
export type Ledger = {
  readonly balance: Cents;
  readonly seen: Readonly<Record<number, Say>>;
};
export type Working = Ledger & { readonly ask: Ask };
```

В `seen` лежит список, из которого берётся ответ на вторую доставку запроса. `ask` есть только в `working`, потому что проверяемый запрос и есть содержание `working`.

## 5. Условия

Условие записывается чистым предикатом от `(context, payload)`. Из-за чистоты `can` возвращает тот же вердикт, что и следующий `dispatch`, и ничего при этом не сдвигает (README, «`can`»).

Условия терминала:

```ts
function payable(c: Typed): boolean {
  return moneyOf(c.typed) > 0;
}

function lastOne(c: Typed): boolean {
  return c.typed.length <= 1;
}

function mine(c: Flight, p: Say): boolean {
  return p.ticket === c.ticket;
}

const yes = (c: Flight, p: Say): boolean => mine(c, p) && p.ok;
const no = (c: Flight, p: Say): boolean => mine(c, p) && !p.ok;
```

В `mine` записан весь протокол. Это не проверка перед выбором действия: от `mine` зависит, произойдёт ли переход, и записан он один раз для обоих правил.

Условия хоста:

```ts
function known(c: Ledger, p: Ask): boolean {
  return p.ticket in c.seen;
}

function mine(c: Working, p: { ticket: number }): boolean {
  return p.ticket === c.ask.ticket;
}

const afford = (c: Working, p: { ticket: number }): boolean =>
  mine(c, p) && c.ask.amount <= c.balance;
```

Две функции `mine` повторяют одно правило на обоих концах: в сообщении есть номер обмена, к которому оно относится, а сообщение с чужим номером ничего не меняет.

## 6. Операции

Каждая операция возвращает контекст того состояния, в которое машина входит. Там, где новое состояние несёт меньше прежнего, контекст собирается заново, а не расширяется: расширение прошло бы проверку типов и перенесло бы поле в состояние, тип которого его не содержит.

```ts
const booked = (c: Typed): Flight => ({
  pan: c.pan,
  ticket: c.ticket + 1,
  amount: moneyOf(c.typed),
});

const asked = (c: Flight) => ({
  ticket: c.ticket,
  pan: c.pan,
  amount: c.amount,
});
```

В одном правиле `booked` стоит на месте `with`, а `asked` на месте `by`. `by` выполняется на достигнутом контексте (README, «Выходные события»), поэтому номер в канале совпадает с номером в `waiting`: одно число, прочитанное один раз, в одном месте.

Операции хоста устроены так же, и одну пару стоит прочесть внимательно:

```ts
const filed = (c: Working, said: Say): Ledger => ({
  balance: said.ok ? c.balance - c.ask.amount : c.balance,
  seen: { ...c.seen, [said.ticket]: said },
});

const spoken = (c: Ledger, p: { ticket: number }): Say => c.seen[p.ticket]!;
```

`filed` записывает ответ, а `spoken` читает его обратно; `spoken` стоит в `by` обоих правил `working`. Сообщение в канале не собирается второй раз рядом с записью: ответ один, лежит в одном месте, и повтор не расходится с оригиналом, потому что это тот же объект.

## 7. Стык: Λ становится Σ

Весь стык занимает шесть строк.

```ts
terminal.rx.on("auth", (ask) => {
  wire.send("down", `auth #${ask.ticket} · ${money(ask.amount)}`, () =>
    host.dispatch("auth", ask),
  );
});

host.rx.on("said", (said) => {
  wire.send("up", `${said.ok ? "ok" : "no"} #${said.ticket}`, () =>
    terminal.dispatch("said", said),
  );
});
```

Выходная буква одной машины становится входной буквой другой без изменений. Ни один модуль не импортирует другой; на оба подписана страница, и это единственное место, где записано, что машин две.

Здесь нет обработки дубликата и нет обработки опоздавшего ответа. Если канал вызовет доставку дважды, `dispatch` будет вызван дважды, и второй вызов отклонят условия из п. 5. Страница читает вердикт и записывает его в журнал (п. 8).

Проверку хоста несёт состояние `working`, а не обещание в коде страницы:

```ts
host.rx.on(TRANSITION, ({ target }) => {
  if (target.type !== "working") return;
  const { ticket } = target.context.ask;
  setTimeout(() => host.dispatch("ready", { ticket }), 500);
});
```

`setTimeout`, а не прямой вызов, потому что вложенный в текущий `dispatch` возвращает `BUSY` (README, «Вложенный `dispatch`»). Пока проверка идёт, хост стоит в `working`, и на диаграмме `working` выглядит таким же состоянием, как остальные.

## 8. Канал

Канал остаётся единственным на этой странице, что не автомат. Сообщение находится в нём заданное время, после чего передаётся получателю; читатель увеличивает это время, включает вторую доставку, отбрасывает сообщение и разрывает связь; ни одно из этих действий не входит в состояние машин.

```ts
export type Deliver = () => Verdict;

export type Wire = {
  readonly weather: Weather;
  send(way: Way, label: string, arrive: Deliver): void;
  readonly flying: readonly Parcel[];
  watch(on: () => void): () => void;
  readonly log: readonly string[];
};
```

`Deliver` возвращает вердикт принимающей машины. Недоставленное сообщение и доставленное, но отклонённое, попадают в журнал разными строками:

```ts
const took = arrive();
const said = `${label}${copy ? " (a copy)" : ""}`;
note(took.isOk() ? `▸ ${said}` : `⊘ ${said} — ${because(took)}`);
```

`because` читает ошибку вердикта (README, «Вердикт») и подставляет строку журнала:

| Ошибка           | Что записано в журнале                           |
| ---------------- | ------------------------------------------------ |
| `UnhandledError` | Правила для события там, где стоит машина, нет   |
| `RejectedError`  | Ни одно условие не выполнилось                   |
| `TerminalError`  | Машина стоит в состоянии без исходящих переходов |
| `BusyError`      | Машина находится в середине перехода             |

Время пересечения задаётся ползунком, и от него зависит, какой из двух случаев дубликата видит читатель. Копия уходит на треть пересечения позже оригинала, проверка хоста занимает 500 мс:

| Пересечение | Разрыв между двумя | Куда попадает копия | Что происходит                            |
| ----------- | ------------------ | ------------------- | ----------------------------------------- |
| 0,2 с       | 67 мс              | `working`           | правила на `auth` там нет — отклонение    |
| 2,4 с       | 800 мс             | `listening`         | срабатывает `known` — ответ берётся из списка |

## 9. Работа из браузера

Каждое действие отправляется прямо в машину, без проверки фазы:

```ts
for (const key of keys)
  key.addEventListener("click", () =>
    terminal.dispatch("key", { digit: key.dataset["key"]! }),
  );
rub.addEventListener("click", () => terminal.dispatch("rub"));
send.addEventListener("click", () => terminal.dispatch("send"));
```

Каждый элемент управления включён тем же вердиктом, который вернёт следующий `dispatch`:

```ts
for (const key of keys)
  key.disabled = !terminal.can("key", { digit: key.dataset["key"]! }).isOk();
rub.disabled = !terminal.can("rub").isOk();
send.disabled = !terminal.can("send").isOk();
giveUp.disabled = !terminal.can("giveUp").isOk();
again.disabled = !terminal.can("again").isOk();
```

Клавиши выключены в `waiting` потому, что в схеме там нет правила на `key`, а не потому, что их отключает строка кода. Уберите правило из таблицы, и клавиша выключится; добавьте правило, и она включится.

## 10. Прогон машин

Один платёж на 5.00 €, канал доставляет и запрос, и ответ дважды. Канал здесь управляется вручную, поэтому порядок шагов записан ниже; на странице порядок задают таймеры. Реальный вывод `log` на обеих машинах:

```text
| machine  | event    | from       | to         | output                         |
| -------- | -------- | ---------- | ---------- | ------------------------------ |
| terminal | key      | idle       | entering   | —                              |
| terminal | key      | entering   | entering   | —                              |
| terminal | key      | entering   | entering   | —                              |
| terminal | send     | entering   | waiting    | auth                           |
| host     | auth     | listening  | working    | —                              |
| host     | ready    | working    | listening  | said                           |
| host     | auth     | listening  | listening  | said                           |
| terminal | said     | waiting    | approved   | —                              |
| terminal | said     | approved   | —          | refused: UnhandledError        |

balance: 245.00 €  terminal: approved  why: charged 5.00 €
```

Три строки несут три свойства из п. 1.

В строке 7 записана копия запроса. Она даёт переход `listening → listening` и выход `said`, поэтому отправитель получает ответ, а остаток равен 245.00 €, то есть 250.00 € минус 5.00 € один раз. Запрос списал однократно.

В строке 9 записана копия ответа. К моменту её прихода терминал стоит в `approved`, где нет правила на `said`, поэтому `dispatch` возвращает `UnhandledError` и ничего не меняется. Ответ относился к одному запросу, и этот запрос закрыт.

Разорвите канал между строками 4 и 5, и строки 5 не будет: терминал останется в `waiting` и покажет это. Таймера в схеме нет, и единственный выход из `waiting` даёт `giveUp`, то есть действие читателя.

## 11. Анализ схем

`validate` по обеим схемам, вывод реального прогона:

```text
===== terminal: validate =====
[]

===== host: validate =====
[]
```

Замечаний нет ни к одной: недостижимых состояний нет, правил, которые всегда перекрывает стоящее выше правило без условия, тоже нет.

`analyze`:

```text
===== terminal: analyze =====
{
  "nodes": ["idle", "entering", "waiting", "approved", "declined"],
  "reachable": ["idle", "entering", "waiting", "approved", "declined"],
  "unreachable": [],
  "terminal": []
}

===== host: analyze =====
{
  "nodes": ["listening", "working"],
  "reachable": ["listening", "working"],
  "unreachable": [],
  "terminal": []
}
```

Поле `terminal` пусто у обеих, и это утверждение о протоколе, а не о коде: ни у одной машины нет состояния, из которого нет выхода. У терминала из `approved` и `declined` ведёт `again`, хост всегда возвращается в `listening`.

Поставьте правило `auth` без условия первым, а правило с `known` под ним, и в выводе `validate` появится `dead-rule`: второе правило не сработает никогда, и каждый повторный запрос будет проверен и списан заново.

## 12. Машины на странице

Каждую машину рисуют виджеты инспектора, поэтому каждый виджет здесь в двух экземплярах:

```ts
const termBand = ensemble(
  fromMachine(terminal, { history: past }),
  { diagram: termDia },
  { focus: termFocus },
);
termBand.enroll(termLegend);
termBand.draw();
```

Здесь два субъекта, две диаграммы и две легенды: по легенде под каждой машиной, чтобы оба набора состояний читались там же, где стоит машина, а не в одном ряду, который пришлось бы подписывать. Запись прогона одна, для терминала: именно его фазами управляет читатель.

Панели самой страницы получают переключатель в том же ряду, что и виджеты:

```ts
for (const [name] of own) desk.seat(name);
```

`seat` регистрирует имя и рисует переключатель, но ничего не показывает: расклад панелей хранит автомат самой библиотеки, а страница читает его. Поэтому один ряд управляет всем экраном, и при выключенных переключателях на экране остаются только две машины и канал.

Док и обе легенды помечены `class="tool"`, а помеченная область показана в палитре Gruvbox, а не
в палитре страницы, и в светлой теме, и в тёмной. Так нарисованное инструментом отличается от
нарисованного приложением. Вся раскраска собрана в блоке custom properties в `shell.css`: палитра
наследуется в теневое дерево, поэтому ни один виджет не правится.

Где стоят панели, решает читатель, а не страница:

```ts
dockEdge(document.getElementById("board")!, "right");
```

`dockEdge` записывает край на `<body>`, а таблица стилей раскладывает док по нему: вдоль правой
стороны или по нижнему краю, если предмет широкий и низкий. Выбор сохраняется для этой страницы.
